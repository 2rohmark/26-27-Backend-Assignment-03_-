# 26-27 Backend Assignment 03 - 예외처리 및 검증
## 과제 배경

수업에서 `GlobalExceptionHandler`에 `Exception`을 처리하는 핸들러를 추가했습니다.
따라서 현재는 별도로 처리하지 않은 예외가 발생하면 모두 `500 Internal Server Error (COMMON_001)`로 응답됩니다.

하지만 아래 [처리해야 할 예외 상황](#처리해야-할-예외-상황)들은 서버 내부의 문제가 아니라 **클라이언트의 잘못된 요청**으로 인해 발생하는 예외입니다.

이번 과제에서는 각 상황을 직접 발생시켜 보고, 서버 로그를 통해 어떤 예외가 발생하는지 확인한 뒤 적절한 예외처리를 추가해 봅시다.

---

## 과제 요구사항

1. 강의 시간에 사용한 실습 프로젝트를 그대로 사용합니다.
2. 아래의 요청을 Postman으로 직접 보내 각 상황을 발생시킵니다.
3. 서버 콘솔에 출력되는 로그를 확인하여 어떤 예외가 발생했는지 직접 찾아봅니다.
4. 확인한 예외를 처리할 수 있도록 `GlobalExceptionHandler`에 `@ExceptionHandler` 메서드를 직접 추가합니다.
5. 각 예외 상황에 적절한 HTTP Status Code와 Error Code를 정의하여 응답합니다.
6. 각 상황마다 서로 구분되는 Error Code를 사용합니다.
    - 클라이언트가 Error Code만 보고도 어떤 문제가 발생했는지 구분할 수 있어야 합니다.
7. 모든 실패 응답은 동일한 공통 응답 형식을 사용합니다. (에러 응답 구조는 자유롭게 수정하셔도 됩니다.)
    - 다음 정보는 필수로 들어가야 합니다.
        - error code
        - message
8. 기존의 `Exception` 핸들러는 삭제하지 않습니다.
    - 별도로 처리하지 않은 예상하지 못한 예외는 계속 `500 Internal Server Error`로 처리되어야 합니다.
9. 구현 후 Postman을 이용해 각 예외 상황이 의도한 응답으로 반환되는지 확인합니다.

> [!NOTE]
> 별도로 로그를 출력하는 코드를 작성할 필요는 없습니다.
> 현재 `Exception` 핸들러에서 예외 정보가 로그로 출력되도록 되어 있으므로, 예외 상황에 대한 요청을 보내고 서버 콘솔을 확인하면 어떤 예외가 발생하는지 알 수 있습니다.

### 처리해야 할 예외 상황

요청을 직접 보내 어떤 예외가 발생하는지 확인하고, 상황에 맞게 처리해 주세요.

| # | 상황 | 요청 예시 | 참고 |
|---|------|-----------|------|
| 1 | 존재하지 않는 URL로 요청한 경우 | `GET /memberz` | |
| 2 | 지원하지 않는 HTTP 메서드로 요청한 경우 | `PATCH /members/1` | 회원 수정 API는 현재 `PUT`만 지원합니다. |
| 3 | 경로 변수에 잘못된 타입의 값을 넣은 경우 | `GET /members/abc` | `memberId`는 숫자 타입입니다. |
| 4 | 지원하지 않는 Content-Type으로 요청한 경우 | `POST /members` | Postman의 Body 탭에서 `raw`를 선택하고, 오른쪽 형식을 `JSON`이 아닌 `Text`로 바꿔서 요청합니다. |
